# 分类与空值排查的分级判断流程

> 分类错和参数空，两类问题都不能"看到就改 dim"。改之前必须走完下面的判断链，**不要跳步**。

---

## 1. 分类核对的三段式判断

某条物料商城分类与我方不一致时，按下面顺序逐层排：

```
1. 商城（得捷/芯查查）给的是哪一类？两个商城都查一下避免单边偏差。
       │
       ├─ 两边一致且与我方不同 → 几乎一定是我方错，进入第 2 步
       │
       └─ 两边自己就不一致     → 回到源数据看厂家原始描述谁更接近，
                                  暂不动规则，记入"待业务裁决"
                │
2. 回到源数据，看可用判定信号在哪个字段：
       本源所有候选字段全部扫一遍
       （icpdf：prajson2 / prajson / category2 / taginfo / note_cn ……
        digikey：category / family / 参数 KV 表 / 其他文本列 ……
        其他源：列出本源全字段清单依次过）
       │
       ├─ 源里有明确信号（如「电容器类型 = ELECTRIC DOUBLE LAYER」）
       │     → 进入第 3 步
       │
       └─ 源里没有任何区分信号
             → 不可解，记入"业务/上游边界"，不要硬写规则强行猜
                │
3. 源里有信号但我方没分对。是规则问题，三种子情况：
       a. dim 里压根没覆盖这个信号写法
          → 加一条新规则。
       b. 已经有规则但没命中 / 被别的规则抢走
          → 检查 phase / priority；把胜者公式 (phase DESC, priority ASC) 套一遍
            看本来该胜的那条排第几。
       c. 规则太宽，把别的类目也吃进来了（产生反向误判）
          → 加约束条件（多字段 AND、加 NOT、收紧关键词），不要扩大原规则。
```

**关键**：第 3 步的 (b) 是最容易踩的坑。phase/priority 改动会**全表回归**，必须配合内部 diff 探针 + 外部样本重核对一次。

---

## 2. 空值核对的四段式判断

某个标准属性空值率偏高时，**不要立刻去补 dim 抽取规则**。按下面顺序逐层排：

```
1. 商城（得捷/芯查查）有没有这个参数？
       │
       ├─ 没有  → 业务上这个参数本来就不公开，正常 NULL，不动。
       │
       └─ 有  → 进入第 2 步
                │
2. 判断：这是 L2 公共属性，还是 L3 专有属性？
       │
       ├─ L3 专有属性（仅该子类需要，如无线协议、NPU 算力、FOC 硬件、安全认证等）
       │     → 进一步判断：是否属于「当前数据源采集范围内」的字段？
       │           ├─ 不在范围内（通用元器件数据库通常不收录此类参数）
       │           │     → 在 dim_attr_schema 保留合约登记，
       │           │       记入"待未来数据补全"，不追、不补规则。
       │           └─ 在范围内 → 继续第 3 步
       │
       └─ L2 公共属性 → 继续第 3 步
                │
3. 回到源数据（本源所有候选字段，按 §2 列出的清单全过）看：源里有没有？
       │
       ├─ 没有  → 再判断：商城值是「厂商实测值」还是「计算 / 派生值」？
       │           ├─ 是派生值 → 考虑未来计算列，不补抽取规则
       │           └─ 是实测值 → 上游采集问题，记入"已知源端缺失"，不补 dim 规则
       │
       └─ 有  → 进入第 4 步
                │
4. 源里有，但是我们窄表 NULL。是我们的抽取规则问题。
       两种子情况：
         a. dim_attr_extract_rule 里没覆盖这条源端键/写法
            → 加一条新的抽取路径。
         b. 覆盖了但单位换算没识别 / 值域越界（min_bound/max_bound）被标 out_of_range 或置 NULL
            → 补单位字典 或 调 schema 的 min_bound/max_bound（宽表残留越界由 DL12 复扫）。
```

**关键**：

- 第 1 步「商城没有」就停手是最容易被忽略的——补一条永远命中不到的规则就是噪音
- 第 2 步 L3 专有属性「不在数据源范围」要在 schema 里**保留合约登记**，仅记入"待未来数据补全"，不要追、不要补规则
- 第 4 步的 (b) 经常被遗漏：抽到了但单位识别不出 → fall-through 成 NULL 或者数值偏差 1000 倍

## 3. 两份外部对照 TSV 模板

每轮迭代两份模板各自留一份。

### 3.1 分类核对 TSV

| 列名 | 含义 |
|------|------|
| 料号 | MPN |
| 品牌 | brandshort |
| 来源 | digikey / 芯查查 |
| 商城 L2/L3 | 商城给的分类 |
| 我方 L2/L3 | 当前 dim 结果 |
| 是否一致 | Y / N |
| 数据源 | icpdf / digikey / mouser ... |
| 源端关键信号字段路径 | icpdf：prajson2.电容器类型 / category2 ；digikey：param_name='电容器类型' ；... |
| 命中规则 ID | rule_id |
| 判定结论 | 见下方四选一 |
| 处理动作 | 加规则 ID / 暂不动 / ... |

**分类判定结论四选一**：

- `consistent`（一致，正常）
- `mall_inconsistent`（两个商城互相不一致，待业务裁决，不动规则）
- `signal_missing`（源里没有任何区分信号 → 业务/上游边界，不写规则强猜）
- `our_rule_gap`（源里有信号但我方判错 → 进改 dim 流程）

### 3.2 参数核对 TSV

| 列名 | 含义 |
|------|------|
| 料号 | MPN |
| 品牌 | brandshort |
| 标准属性 code | std_attr_code（如 `capacitance_f`） |
| 来源 | digikey / 芯查查 |
| 商城是否有该参数 | Y / N |
| 商城值 | 实际值（含单位） |
| 数据源 | icpdf / digikey / mouser ... |
| 源数据是否有 | Y / N |
| 源端字段路径 | icpdf：prajson2.电容 ；digikey：param_name='电容值' ；... |
| 我们的窄表值 | EAV 的 `value_std_double` / `value_std_varchar` |
| 判定结论 | 见下方三选一 |
| 处理动作 | 加规则 / 不补 / ... |

**参数判定结论三选一**：

- `business_not_public`（商城都没有，正常）
- `upstream_missing`（商城有 + 源端没有 → 上游问题）
- `our_rule_gap`（商城有 + 源端有 + 我们没抽出 → 自己的问题）

### 3.3 通用纪律

只有 `our_rule_gap` 才进入「改 dim」的工作流；其它类型要单独归档，避免反复浪费时间在不可能修好的 case 上。

TSV 文件命名建议：

```
artifacts/<l1>/<l1>_class_review_<YYYYMMDD>.tsv
artifacts/<l1>/<l1>_attr_review_<YYYYMMDD>.tsv
```

每轮迭代落一份，git 跟代码一起入仓，方便后人回看「当时为什么提了这条规则」。
