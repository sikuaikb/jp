## LL-20260601-01 · 把 `schema_version` 当成规则迭代号（v1.0.00/v1.1.00/v1.2.00），而非 Excel schema 版本

**日期**：2026-06-01  
**场景**：mcu_mpu_dsp 沙盒收窄 MPU/DSP fallback 时，新规则写 `schema_version=v1.2.00`，分类树里 MPU 节点仍是 `v1.0.00`、MCU/DSP 是 `v1.1.00`。用户纠正：`schema_version` 应与品类 Excel schema 版本一致——`tmp/mcu_mpu_dsp_schema_v5.20.xlsx` 按命名约定是 **`v1.5.20`**（文件名省略前缀 `1.`），不是规则改动序号。

**错误行为**：
- 把 `schema_version` 当「这条规则是第几版迭代」或「某次 taxonomy 小改的版本号」随意递增。
- 同一 L1 内分类树与规则 CSV 混用多个 `schema_version`（MPU v1.0.00 / MCU v1.1.00），引擎 `INNER JOIN ... ON schema_version` 静默零产出（MPU 收窄后仅 29 行）。
- 属性 dim 又用第三套命名 `mcu_mpu_dsp_schema_v1.0`，与分类层完全不对齐。

**后果**：
- 规则看似 enabled、校验 C3 orphan 也通过，但 classify 引擎 JOIN 失败 → 整批规则不命中。
- 协作者无法从 `schema_version` 反查对应哪份 Excel schema，版本治理失效。

**根因**：
- 方法论未写清「schema_version = Excel 规格版本」；电阻 prod 已用 `v1.5.20` 但未在 mcu 沙盒复用同一约定。
- 缺少机械门控拦截「同一 L1 多 schema_version / 规则与分类树 version 不一致」。

**纠正与防御**（新硬约束）：
1. **分类 dim + 规则 dim**：`schema_version` 统一 = 品类 Excel 文件名版本（`{l1}_schema_v5.20.xlsx` → `v1.5.20`）；**禁止**用 v1.0.00/v1.1.00 等规则迭代号。
2. **属性 dim**：`schema_version` = `{l1}_schema_v1.5.20`（与电阻 `resistor_schema_v1.5.20` 同模式）；数值段与 Excel 一致。
3. **机械门控 `validate_classify_dim.py` C10**：同一 l1 分类树仅允许一个 schema_version；enabled classify 规则的 version 必须与其 l3_id 在分类树中一致。

## LL-20260529-17 · 删 L3 节点后留下跳号（190301+190304），L2/L3 id 体系不连续

**日期**：2026-05-29  
**场景**：把 DSP 三个子类合并成单一 `general_programmable_dsp` 后，dsp 段只剩 `190301`(general) 与 `190304`(audio)，中间 `190302/190303` 空缺。用户要求「L2 和 L3 的 id 要在自己的体系中逻辑自洽，且需要连续」。

**错误行为**：
- 合并/删节点时只删不重排，把 `190302/190303` 直接挖空，留下 `190301 → 190304` 的跳号。
- 把 l3_id 当成「一次分配后永不回收」的稳定键，忽略了**同一 L2 内 L3 编号应连续**这一自洽要求。

**后果**：
- dsp 段 id 不连续，体系不自洽；后续看 id 无法判断该 L2 有几个 L3、是否有遗漏。

**根因**：
- 没有「L2 内 l3_id 连续」的机械门控，删节点后无人拦截跳号。

**纠正与防御**（新硬约束）：
1. **同一 (l1_code, l2_code) 内的 l3_id 必须连续无跳号**（数值排序后相邻差=1，剔除 `*_unclassified`）；删节点后必须补齐重排（本次 `audio_dsp` 190304→190302，dsp 段恢复 190301/190302 连续）。
2. **机械门控 `validate_classify_dim.py` C8**：按 (l1,l2) 分组校验 l3_id 连续性，跳号即 FAIL 并报缺号。
3. 编号结构约定：`<L1 2位><L2 2位><L3 2位>`，L3 在每个 L2 内从 `01` 连续递增。

## LL-20260529-16 · 把 `dim_l3_classify_all.sql` 当成 L1/L2/L3 全维度权威，校验器拿它比对 L2/L3

**日期**：2026-05-29  
**场景**：用户多次强调「`dim_l3_classify_all.sql` 仅供参考，只有里面的 **L1 代码**是准确的；L2/L3 都以品类 Excel schema（`mcu_mpu_dsp_schema_v5.20.xlsx`）为准」。我却一直把这张 SQL 表当成 L1/L2/L3 三层全维度权威：`validate_classify_dim.py` 的 C1 用 `(l1_code,l2_code,l3_code)` 三元组逐字段比对该表，导致 capacitor/resistor 等品类只要 L2/L3 命名与该表（过时部分）不一致就 FAIL。用户纠正：「硬门控里校验 L1 的分类和 id 是否正确就行」，且因协作者不一定有 Excel，**校验器不得依赖 Excel、也不得用该 SQL 表校验 L2/L3**。

**错误行为**：
- 把「参考表」误当「三层权威表」，C1 比对到 l2_code/l3_code 字面。
- 没区分该表的「L1 维度（准确）」与「L2/L3 维度（仅参考、可能过时）」。

**后果**：
- C1 产生大量假阳性 FAIL（capacitor/resistor 的 L2/L3 改名即红），淹没真正的 L1/id 段问题（pmic 误用 clock_timing 的 23 段）。
- 若据此「对齐」会反向把 Excel 维护的正确 L2/L3 改坏。

**根因**：
- 未确认「权威边界」——同一张表不同列的权威等级不同：L1 准、L2/L3 仅参考。
- 校验器把「可机械判定」误等同于「拿手头最全的表逐字段比」，忽略了协作者环境（无 Excel）。

**纠正与防御**（新硬约束）：
1. **`dim_l3_classify_all.sql` 只对 L1 维度权威**：只用于「合法 L1 集合 + 每个 L1 的 l3_id 段（前2位一对一）」；L2/L3 以各品类 Excel schema 为准，该表 L2/L3 仅参考。
2. **`validate_classify_dim.py` C1 只校验「l1_code 合法 + l3_id 段归属」，绝不比对 L2/L3**；校验器零 Excel 依赖（协作者无 Excel 也能跑硬门控）。
3. **`validate_dwd_data.py` DC2 比对的是分类树 dim 表自己（L2/L3 已按 Excel 维护），不是 dim_l3_classify_all**，属「结果↔本品类分类树自洽」，保留全字段一致。

## LL-20260529-15 · 合并时没把 DSP 的 L3 对齐 main，机械套用旧 taxonomy 的 fixed/float/multi 四拆分

**日期**：2026-05-29  
**场景**：用户要「mcu/mpu/dsp 的 L3 分类以 main 为准」。main 的 DSP L3 已收敛为**单一** `general_programmable_dsp`（220105，note 明写「合并原 Fixed_Point/Floating_Point/Multicore 三节点；定点/浮点/核心数改为属性字段」）+ `audio_dsp`（220104）。我却以本分支 `foundation/dim_l3_classify_all.sql` 里**遗留的旧拆分** `fixed_point_dsp(190301)/floating_point_dsp(190302)/multicore_dsp(190303)/audio_dsp(190304)` 为准，把 main 的 220105 一条 L3 拆映射成了 190301/302/303 三条。用户强烈纠正：「全部按 main 的 general_programmable_dsp L3 来做，不要有 fixed/float/multi」。

**错误行为**：
- 「L3 以 main 为准」被我理解成「L3 节点集合用本地 taxonomy 文件的形态」，方向搞反。
- 没有先 diff `git show main:` 的 DSP L3 节点，直接拿本地 `dim_l3_classify_all.sql` 的旧四拆分当权威，且本地 rule 的 note 里其实已写「现统一指向 General_Programmable_DSP」却仍保留三个不同 l3_id。
- 把「定点/浮点/多核」这种**属性维度**（arithmetic_type / dsp_core_count / has_floating_point）误当成 **L3 分类维度**，违反 taxonomy 与属性分层。

**后果**：
- 分类层产出 3 个本不该存在的 DSP L3，`dim_attr_schema` 只有 `general_programmable_dsp` → DX1 恒 FAIL（fixed/float/multi 三个 L3 的 ext_attributes 注定恒空）。
- foundation taxonomy / 两份分类树 / 两份 rule csv 五处不一致，污染面广。

**根因**：
- 合并「以 X 为准」时没有以 X（main）的实际产物做 diff 基线，而是拿本地遗留文件当权威。
- 没区分「分类维度」与「属性维度」：能用属性字段表达的差异（定点/浮点/多核）不应拆成独立 L3。

**纠正与防御**（新硬约束）：
1. **DSP 的 L3 只有 `general_programmable_dsp` + `audio_dsp` 两个节点**；`fixed_point_dsp` / `floating_point_dsp` / `multicore_dsp` 一律禁止作为 L3，定点/浮点/核心数走属性字段（`arithmetic_type` / `has_floating_point` / `dsp_core_count`）。
2. **「L3 以某分支为准」= 以该分支的实际 L3 节点集合为基线**，动手前必须 `git show <branch>:<taxonomy 文件>` diff 出 L3 集合，不得拿本地遗留文件当权威。
3. **能用属性字段区分的差异不得拆成 L3**：拆 L3 前先问「这是分类维度还是参数维度」，参数维度归 ext_attributes/属性列。

## LL-20260529-13 · skills 内的校验器必须零外部依赖、可独立运行；新门控不强行接 run_test.sh

**日期**：2026-05-29  
**场景**：为 LL-20260529-12 的「分类 L3 ↔ 属性 L3 覆盖」门控写校验器时，我默认要把它接进沙盒 `run_test.sh`。用户纠正：新门控要加进校验脚本，但**不接 run_test.sh**；且**skills 必须可独立运行，不依赖 skills 目录以外的任何文件**（三个感叹号强调）。

**错误行为（认知）**：
- 把校验器与具体沙盒 `run_test.sh` 绑定，默认它要 import / 读取 `sql_scripts/` 下的 CSV、DDL、build 等外部文件。
- 这会让 `.cursor/skills/component-etl-methodology/tools/` 的校验器**离开本仓库特定目录就跑不起来**，违背"skill 是可移植方法论资产"的定位。

**后果**：
- 校验器一旦依赖 skills 目录外文件，换一个项目 / 换一份 sql_scripts 布局就失效，无法作为通用方法论工具复用。
- 与 run_test.sh 强耦合后，沙盒脚本一改，校验器跟着坏。

**根因**：
- 混淆了「方法论资产（skills/，必须自包含、可移植）」与「某次落地的施工脚本（sql_scripts/，项目专属）」两层边界。

**纠正与防御**（新硬约束）：
1. **skills/ 下的一切可执行物（tools/*.py 等）必须零外部文件依赖**：只允许 import Python 标准库 + 已声明的 pip 包（如 pymysql）；**禁止** `sys.path` 指向 skills 目录外、**禁止**读取 skills 目录外的文件路径。一切输入通过 CLI 参数（连接串、schema、表名、L1 code 等）传入。
2. **校验器自带兜底**：缺参数 / 缺表 / 缺字典一律降级 WARN 跳过并打印用法，禁止裸异常或栈回溯（沿用既有提示规约）。
3. **门控校验器与 run_test.sh 解耦**：校验器是独立可调用脚本；是否接进某个沙盒 `run_test.sh` 由该沙盒自行决定，方法论侧不强制、默认不接。

## LL-20260529-12 · 分类层产出了 L3，属性层却没建 L3 schema → ext_attributes 恒空且无人察觉

**日期**：2026-05-29  
**场景**：用户要求对照电阻基准，检查电容（digikey/icpdf）的 L3 属性有没有写入。

**错误行为**：
搭电容沙盒时，**阶段 3（属性 dim）只建了 L2 层 schema 就推进到阶段 4/5**：
- `dim_attr_schema_capacitor.csv` 83 行**全是 `scope_level=l2`，0 行 l3**；`dim_attr_extract_rule_capacitor.csv` **0 条 L3 抽取规则**。
- 四张 `build_dwd_l2_capacitor_*.sql` 把 `ext_attributes` 写死成 `parse_json('{}')`，未接电阻那套 `scope_level=l3 → ext_attributes` 透视。
- 宽表 DDL 注释留了「当前无 L3 entries，ext_attributes 暂为空 JSON」的 TODO，**但从未回填**。

而分类层（`dim_l3_classify_capacitor`）已实打实产出 5 个 L3 子类（ceramic / film / solid_electrolytic / aluminum_electrolytic / adjustable，合计百万级行）。

**后果**：
- 四张 L2 宽表 `ext_attributes` **恒为 `{}`**，L3 专有信息（陶瓷温度系数 C0G/X7R/Y5V、铝电解负载寿命@温度 / 纹波寿命、薄膜 dV/dt 等）全部丢失。
- 对照电阻基准（65 行 L3 / 12 子类）属于整层缺失，却因 `run_test.sh` 全绿而**静默存在**，直到人工比对才暴露。

**根因**：
1. 阶段 3 未完成（只 L2 不 L3）就推进，把 L3 当"暂缓 TODO"且再没回填。
2. `parse_json('{}')` 硬编码占位是危险信号，但没被当作"未完成"拦下。
3. **最关键**：缺少「分类产出 L3 ↔ 属性 schema L3」的**交叉一致性机械门控**——已有校验只查 orphan rule（规则→schema），没查反向（分类 L3 → 是否有属性 schema 覆盖），所以 gap 无人报警。

**纠正与防御**（新硬约束）：
1. **新机械门控**：对每个 L1，`dwd_component_class.l3_code`（去除 `%_unclassified`）的 DISTINCT 集合，必须被 `dim_attr_schema` 中 `scope_level='l3'` 的 `scope_code` 覆盖；未覆盖的 L3 = ERROR（注定 `ext_attributes` 全空）。接进 `validate_dwd_data.py`（连库 C×A 交叉）/ `validate_pipeline.py`。
2. **`parse_json('{}')` / 写死空 ext_attributes 视为"未完成标记"**：出现即判定该 L2 build 未过阶段 3，禁止进入阶段 6 发布门控。
3. **区分「漏做」与「范围内未做」**：icpdf 电容（43.8 万行源数据）属于本 digikey 单源沙盒的计划外项，需显式立项接入（按 §二-A 接入新源步骤），不与 L3 缺口混为一谈。

## LL-20260529-11 · 新增校验的「权威值」必须有真权威源；不得用同一段脏文本/产出数据反推

**日期**：2026-05-29  
**场景**：盘点枚举受控词表盲区时，我提议给 `dim_attr_schema` 新增 `enum_values` 列来做枚举校验。用户反问「你新增字段的值我从哪里获取呢？数据来源还是一样的啊！」

**错误行为**：提议新增字段却没回答"值从哪来"。若值仍来自库里脏数据或同一段 `value_domain` 自由文本，等于用脏数据定义"什么是干净"，是循环依赖、伪标准（这正是 `value_map` 稀疏不可信的根因）。

**后果**：差点造出一个"看起来有校验、实则拿不到可信基准"的空壳字段。

**根因**：把"加一个字段"当成了解决方案，忽略了校验基准必须有**独立于被校验数据的权威源**。

**核实结论**：
- 枚举/词表的唯一权威源是**用户最初提供的 Excel 规格**（`值域约束` 列），而 dim 的 `value_domain` 就是从它来的——**同源**，新建字段不带来任何新信息。
- 更糟：Excel `值域约束` **自身自相矛盾**（如 `LifeCycle_Status` 三套词表、`AEC/MSL` 分隔符 `/` vs `,` 漂移、`/` 在"符合JEDEC/IPC规范"里非枚举义）。直接 auto-parse 会原样继承冲突。

**纠正与防御**：
1. **铁律**：新增任何"对照/白名单/词表"类校验前，先回答三问——值的权威源是谁？是否独立于被校验数据？源自身是否一致？三问不过则不新增字段、不做校验。
2. 枚举/L3 值词表的可信化**靠人工裁决**，不靠解析自由文本；产出物落 **test_dim 只读对照临时表**（如 `tmp_attr_enum`），**禁止同步 prod dim**（不污染生产 schema）。

- `test_dim.dim_std_brand` 从原本可能已有数据被清成 **0 行**
- `test_dim.v_std_brand_alias` 视图随之为空
- 所有 L2 宽表 `brand` 全部回退 raw `brandshort`、`brandid` 全 NULL
- 品牌门控（`distinct_brand = distinct_brandid`）失败
- 影响范围超出电容试点（任何依赖 `test_dim.dim_std_brand` 的其它 L1 都受影响）

**根因**：
- 误把"品牌字典同步"当成试点 sandbox 的一部分；其实它是**跨 L1 共享的基础设施**，由权限人**离线一次性**维护
- 脚本 `sync_dim_std_brand.sh` 是"先 DROP 后 INSERT"的非幂等危险序列，失败时无回滚
- 没有事先检查 `test_dim.dim_std_brand` 是否已有数据

**纠正与防御**（新硬约束）：

1. **试点流程禁止触碰品牌字典**  
   品牌字典（`dim_std_brand` / `v_std_brand_alias`）是**全局共享只读资源**，所有 L1 试点 / 沙盒脚本**只 SELECT，不 sync、不 DROP、不重建**。

2. **品牌字典维护是独立流程，不进 run_test.sh**  
   - 维护入口：`sql_scripts/2.attribute_standard/sync_dim_std_brand.sh`，由**有 ods 读权限的人**离线触发  
   - 任何 L1 试点的 `run_test.sh` / `e2e.sh` 都不得调用该脚本  
   - 维护流程见 `CONTRIB_BRAND.md`

3. **遇到品牌字典为空 / 缺别名**  
   - **不要**自动 sync，**不要**自动重建  
   - 报告用户："字典缺数据 / 缺别名 X 个，请通知有权限的人补，或提供快照导入"  
   - 跑 L2 build 时用 `SKIP_BRAND_SYNC=1`（或类似显式开关）继续，但需明确告知品牌门控暂时过不了

4. **任何"先 DROP 后 INSERT"脚本，必须在调用前确认表是否已有重要数据**  
   - 若有数据且无可恢复来源，禁止运行  
   - 这是 Agent 的预检责任，不是脚本的责任
