## 3. 重点关注：`dimensions` JSON 分析

**分析口径（均以「每一行」为粒度）**

- **每行键数** `K`：`json_length(dimensions)`，即该行 JSON 对象顶层 key 的个数。
- **每行真实键数** `R`：该行 `dimensions` 中，value **不是**占位符的 key 个数。占位符定义为：`NULL`、空串 `''`、`-`、`--`、字符串 `null`（与源端 `"null"` JSON 解析一致）。
- **每行填充率** `F`：`F = R / K`（当 `K = 0` 时该行不参与填充率分档；本表无 `K=0` 样本）。

**样本范围**：`dimensions IS NOT NULL` 共 **2,491,748** 行；另有 **115,369** 行 `dimensions IS NULL`，不参与下列键数/填充率统计。

### 3.2 每行填充率 `F = R / K`（行级汇总统计）

在 **2,491,748** 行上，对每行先算 `R`、`K`，再对 `F` 做分布：

| 指标 | 值 |
|------|------|
| 每行填充率 min / avg / max | **0** / **0.8599** / **1** |
| p50 / p90 / p99 | **≈0.889**（8/9） / **1** / **1** |

**解读**：

- **平均填充率约 86%**：典型一行里，约 **14% 的 key** 仍是占位符（以 `-` 为主）。
- **中位数约 88.9%**：多数行接近「9 个真实值 / 10 个键」这类比例；**p90、p99 均为 1**，说明长尾里大量行已经 **100% 非占位**。
- **min = 0**：存在少数行所有 value 均为占位符（见 §3.3 左端直方图）。

## 6. 与 `dwd_icpdf_component_param` 交叉对比

### 6.1 两表规模对照

| 指标 | `dwd_ecloud_component_detail` | `dwd_icpdf_component_param` |
|------|------------------------------|------------------------------|
| 行数 | 2,607,117 | 6,831,632 |
| 去重主键值 | 2,589,050 名（`name`） | 6,593,127 型号（`partno`） |
| 参数字段 | `dimensions`（JSON 对象） | `prajson` (JSON 数组) + `prajson2` (JSON 对象) |
| 粒度 | **每组件一行** | **每组件每 PDF 一行**（同 partno 可能多行对应多个 PDF） |

### 6.2 型号交集（按去重 `name` vs 去重 `partno`）

| 指标 | 值 |
|------|------|
| ecloud 去重 `name` | 2,589,050 |
| icpdf_param 去重 `partno` | 6,593,127 |
| **两端都出现的型号** | **596,051** |
| → 占 ecloud 型号 | 23.02% |
| → 占 icpdf 型号 | 9.04% |

### 6.3 行级交集（ecloud 行能否在 icpdf 找到参数）

| 指标 | 值 |
|------|------|
| ecloud 行能在 icpdf_param 找到匹配 partno | **607,602 行** |
| 占 ecloud 总行数 | **23.30%** |

### 6.4 互补：ecloud 缺 `dimensions` 时能否从 icpdf 补救？

| 指标 | 值 |
|------|------|
| ecloud `dimensions IS NULL` 行 | 115,369 |
| 其中能在 icpdf_param 找到 partno 的行（可补救） | **20,311** |
| → 补救率 | 17.61% |

### 6.5 去重型号在"参数覆盖"意义上的分布

| 群 | 去重型号数 |
|------|-----------|
| 两边都有参数（ecloud `dimensions` ∧ icpdf `prajson\|prajson2`） | 576,998 |
| 仅 ecloud 有参数（icpdf 无此型号或无参数） | 1,899,268 |
| 仅 icpdf 有参数（ecloud 无此型号） | 6,016,129 |

**结论**

- 两表覆盖域**重叠不大**：ecloud 的型号主要是平台侧采集的中游商品 SKU（带中文品牌前缀），icpdf 的 partno 主要来自原厂规格书（含大量后缀变体）。  
- 真正意义上的**可以交叉补值**的型号只有约 **58 万个**；剩下的 577+ 万 icpdf 独有型号对 ecloud 来说是"可发现未覆盖"的器件池。  
- 下游 DM 建议：  
  1. 以 `ecloud.name` 作为主索引，LEFT JOIN `icpdf_param on name = partno` 取最全的 `prajson2`；  
  2. 反向：用 `icpdf` 独有型号做"缺失器件候选池"，反哺 ecloud 爬虫目标队列。
