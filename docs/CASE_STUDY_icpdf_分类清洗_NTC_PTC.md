# 案例分享：元器件分类清洗不是「关键词 + 大模型」就能一次到位

## 背景

我们将 **icpdf** 的元器件数据，按自有 **分类体系** 与 **属性规范** 做标准化映射。当前链路里，一部分规则来自 **关键词匹配**；关键词则由大模型基于 icpdf 侧的分类/关键词与我们的目标关键词，抽取 **映射规则** 后落地。

粗看这是一条「自动化程度高」的管道；但在真实数据里，很快会遇到 **粒度不对齐** 与 **单一信号不足以决策** 的情况。

## 问题：粗分类拆不成细分类

在 `dwd_icpdf_component_param` 中，存在一类数据归在：

> **温度相关电阻器（NTC / PTC）**

而我们在业务上需要更细的粒度的标签，例如：

- **NTC 热敏电阻**
- **PTC 热敏电阻**

若 **只依赖关键词**（或仅依赖粗分类名本身），无法稳定区分 NTC 与 PTC——因为上游把二者放在同一「桶」里，文本层面往往缺乏足够区分度。

这说明：**不是所有的映射都能用「分类名 / 描述关键词」穷举解决**；必须在规则设计上预留 **多字段、多条件** 的空间。

## 解决过程：人工下探 + 属性联合规则

对「温度相关电阻器（NTC / PTC）」相关行做 **人工探查**（直连数仓查询、抽样读真实记录），发现 `parjson2` 等结构化字段中存在可用信号，例如：

```json
"电阻器类型": "PTC THERMISTOR"
```

由此可将规则从「仅靠关键词命中粗类」升级为：

- **粗类 / 关键词**（缩小候选集）
- **+ 属性值联合判定**（在候选集内做 NTC vs PTC 的切分）

这条路径的价值不在于「写一个 if」，而是证明：**规则有效性来自对真实字段分布的理解**，而不是对文档里分类名的想象。

## 结论与启示

1. **大模型输出的关键词/映射规则是起点，不是终点**  
   生成式模型擅长归纳表面文本模式，但容易漏掉 **结构化属性**、**同桶多义**、**业务粒度升级** 等问题。

2. **数据清洗需要「规则设计」而不仅是「规则生成」**  
   当粗类无法支撑细类时，要显式引入 **属性联合规则**、**优先级**、**fallback** 与 **可解释的中间结果**（便于复核）。

3. **人工介入是必要成本，且应发生在「对的环节」**  
   与其在下游大面积返工，不如在 **探仓、抽样、打样规则** 阶段投入；这里的 ROI 往往高于无限堆模型 prompt。

4. **这是一个反直觉但很典型的案例**  
   「有 LLM 了为什么还不快」——因为 **真实 ETL/清洗** 的限制条件在数据形态与业务粒度，不在写作文能力。

---

*适用场景：元器件类目治理、多来源属性归一、粗类到细类的规则沉淀、LLM 辅助但需可审计的数据生产流程。*
